# Хранение видео и сервер

## Выбранное владельцем решение

**Все видео хранятся на том же сервере, где работает Stream Panel.** Предложение обязательного внешнего S3-хранилища владелец отклонил. Не возвращать его в архитектуру как согласованную зависимость.

Загружается один исходный файл; три площадки не требуют трёх постоянных локальных копий. Временные файлы обработки при необходимости должны учитываться в дисковом бюджете.

## Когда удалять

1. Получить подтверждённый успех публикации YouTube.
2. Получить подтверждённый успех TikTok.
3. Получить подтверждённый успех Instagram.
4. Сохранить файл ещё **24 часа после последнего из трёх успехов**.
5. По истечении этого времени файл можно автоматически удалить.

Формула: `eligible_for_deletion_at = max(success_at_youtube, success_at_tiktok, success_at_instagram) + 24 часа`, только когда все три успеха подтверждены.

Нельзя отсчитывать сутки от загрузки в панель, общего планового времени, первого успеха, приёма файла API или неудачной попытки.

Если хотя бы одна площадка не опубликовала ролик, файл остаётся, включая случаи длительного догоняния. После рестарта срок должен восстанавливаться из базы.

В раннем ответе владелец согласился, что явный ручной отказ от публикации на проблемной площадке может снять удержание файла. Точный интерфейс, подтверждение и начало отсчёта для такого исключения пока не определены; это не автоматическое удаление при ошибке и не заморозка площадки.

24 часа — запас на возможную поломку после публикации. Это не гарантия восстановления состояния соцсетей и не требование автоматически переопубликовывать исчезнувшие посты.

## Что известно о VPS

В [документации Stream Panel](https://github.com/thesmithmode/Stream-Panel/blob/main/docs/ops/server.md) записан первоначальный read-only preflight:

- Ubuntu 24.
- Примерно 3,4 GiB RAM, около 2 GiB доступной RAM на момент проверки.
- Около 16 GiB свободного диска на момент проверки.
- Уже работающий HTTPS reverse proxy Traefik на 80/443.

Эти числа **исторические**, не текущие измерения. Новый проект не должен обещать достаточную вместимость по старому preflight. В этой задаче live-доступ к VPS и текущие ресурсы не проверялись.

Существующая Stream Panel хранит свою базу, временные данные, версии и резервные копии. Всё исторически свободное место нельзя отдать Shorts Panel.

## Оценка места

Для среднего размера файла S и N уникальных роликов очередь занимает примерно `N × S`, плюс опубликованные за последние сутки, незавершённые публикации, временные файлы и служебные данные.

| Очередь при условных 100 МБ на файл | Только исходники |
| --- | --- |
| 7 видео | 700 МБ |
| 21 видео | 2,1 ГБ |
| 100 видео | 10 ГБ |

Это арифметические примеры, не измеренный средний размер пользовательских видео. Задержки TikTok или заморозка площадки могут увеличить удержание намного больше суток.

## Защита совместного сервера — предложения реализации

- Отдельная служба/процесс, отдельные каталог данных и база; конкретный стек пока не выбран.
- Контролировать свободное место перед загрузкой, во время записи и перед операциями с временными копиями.
- Ограничить бюджет новой панели и оставить резерв системе и Stream Panel. Значения выбрать после свежего preflight.
- При нехватке места отказать новой загрузке с понятным сообщением; не удалять неопубликованные ролики для освобождения места.
- Загружать и отправлять файлы потоково, не держать целые видео в RAM.
- Не включать тяжёлое перекодирование как обязательную часть первого выпуска.
- При необходимости отдавать файл платформе через HTTPS-ссылку с ограниченным сроком, доступную без пользовательской cookie. Файл по-прежнему остаётся на этом VPS.
- Не складывать видео в Git и не размножать их автоматически в многочисленных копиях базы.
- Резервное копирование базы расписания/токенов и защита самих исходных видео — разные задачи. Политика бэкапа видео пока не выбрана.
- Очистка должна проверять активные операции и удалять только принадлежащие новой панели файлы.
- Не менять каталоги, резервные копии, службу и proxy-конфигурацию Stream Panel без задачи на deployment.

## Пока открыто

Максимальный размер файла, общий лимит очереди, резерв диска, точные ограничения CPU/RAM, необходимость видеобэкапов и поведение при ручной заморозке. Эти настройки не мешают сейчас зафиксировать выбранное локальное хранение.
