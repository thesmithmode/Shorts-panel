# Разработка в dev: план и критерии

## Политика владельца

- Весь код и изменения проекта отправляются в `dev`. В `main` сейчас ничего не отправлять.
- Production deployment допускается исключительно из `main`; push в `dev`, PR, ручной запуск с другой ветки не могут разворачивать production.
- Для нового поведения и исправлений сначала написать тест и увидеть ожидаемый отказ, затем реализацию.
- Покрытие строк, функций и ветвлений тестируемого кода — не ниже 90%. Показывать точную область измерения; не выдавать покрытие только scheduler за покрытие приложения. Непокрытые HTTP/UI/API-адаптеры — незавершённая работа, а не исключения ради процента.
- Edge cases обязательны: границы времени МСК, пропуски, рестарты, неоднозначный внешний результат, истечение токена, диск, повторы, ручные изменения.

## Исходные проблемы (исторический список)

Это исходная инвентаризация, не список незавершённых задач. Последующие разделы фиксируют исправления; актуальные ограничения перечислены в конце документа.

1. Engine зависит от конкретных Store/Providers; тесты используют небезопасные `as unknown as Providers`. Выделить узкие интерфейсы репозитория/публикации и внедряемые часы.
2. `parseMoscow` использует Date.parse, допускающий нормализацию несуществующих дат. Сначала добавить тесты на 30 февраля, формат и границы, затем строгую проверку.
3. Вычисление горизонта зависит от количества роликов, а не расстояния до защищённого первого ролика: дальняя дата может оставить очередь без назначений. Зафиксировать тестом.
4. Неоднозначные ошибки публикации правильно не повторяются, но безопасные ошибки до отправки требуют отдельной классификации и автоматического восстановления.
5. HTTP-код объединяет авторизацию, загрузки, OAuth и очередь в одном модуле. Разделять по функциональной ответственности после контрактных тестов.
6. Нет измеренного покрытия всего приложения. Ввести отчёт и не утверждать достижение 90% без фактических результатов.
7. Нет production workflow; создать отдельный gate, связанный с успешной проверкой точного main SHA, без запуска из dev.

## Последовательность

1. Перевести разработку на dev, записать правила и развести CI/deployment.
2. Измерить покрытие существующих тестов; добавить edge cases для планирования/хранения/engine.
3. Исправить доказанные ошибки через red → green; выделить интерфейсы без изменения поведения.
4. Покрыть адаптеры сетевыми контрактами с подменой transport, затем разнести HTTP на тестируемые маршруты.
5. Добавить компонентные и браузерные проверки UI; объединить измерение backend/frontend, включить 90% gate без обхода файлов.
6. Проверить живые OAuth и разрешённый путь TikTok; получить доступ к целевому VPS, обследовать только read-only.
7. Готовить main-релиз только после явного решения владельца. Сейчас main не менять.

## Принципы

KISS: без универсального фреймворка задач и лишних слоёв. SOLID: интерфейсы по фактическим потребителям, отдельно планирование, хранение, внешняя публикация и HTTP. Переиспользовать модель площадок, время, валидацию и политику повторов; не дублировать правила в UI и backend.

## Текущее измерение и gate

`npm run coverage` объединяет c8/V8 для серверного кода и Istanbul-инструментацию для UI. В область входит весь `src/`, без исключения непокрытых файлов. Браузерные сценарии работают с реальным локальным сервером, а ошибки/неоднозначные состояния дополнительно проверяются через контрактные ответы. Для UI проверяется наличие настоящих счётчиков функций: синтетическое «100% без функций» не принимается.

Порог из `.c8rc.json` применяется к объединённому отчёту для строк, statements, ветвей и функций; меньше 90% не допускается. Промежуточный c8-этап пишет JSON без отдельного gate, потому что он ещё не содержит UI-счётчиков. `coverage:report` — диагностический режим; CI использует только строгий `coverage`. Обычная production-сборка восстанавливается в finally после инструментированной проверки.

Production workflow слушает только успешный push-CI ветки main, перепроверяет точный текущий SHA, скачивает artifact того же CI и использует отдельный production environment. Дополнительный выключатель `SHORTS_PRODUCTION_ENABLED` остаётся выключен до настройки и проверки изолированного серверного receiver. Секреты Stream Panel не переиспользуются. Ветка dev не может выпустить release artifact для production.

Предыдущее измерение: 100 тестов приложения, браузерные сценарии, TypeScript и production build проходили; строки 98.44%, statements 98.19%, ветви 93.25%, функции 96.25%. Актуальная проверка новой итерации приведена в конце документа. Отдельные Python-тесты deployment не входят в процент покрытия src.

## Сделано после ревью

- HTTP выделен в `createApplication`, запуск процесса/таймера — в index; тесты используют настоящую временную SQLite и локальный HTTP без сетевых публикаций.
- Сетевые контракты проверяют OAuth, обновление токенов, обработку YouTube/Instagram, неполные ответы и ошибки. Неполный refresh не затирает рабочие токены.
- Подтверждённая Instagram-публикация сохраняется до необязательного получения permalink, чтобы ошибка ссылки не вызвала повторный пост.
- Проверка вертикального видео вынесена в общий валидатор с тестами границ длительности и размеров.
- UI восстанавливается после ошибки самого первого запроса состояния; добавлена кнопка повторной загрузки.

## Оставшиеся зависимости и последующие этапы

Текущая задача ограничена репозиторием: сервер не трогать и deployment не выполнять. Живые OAuth/публикации и TikTok требуют внешних приложений/прав и не заменяются моками. Автохэштеги, заморозка площадки и дальнейшее выделение маршрутов остаются отдельными задачами. 90% покрытия не является доказательством готовности внешних интеграций или production.

## Стабилизация после ревью

- После простоя более часа новые задания получают исходное время слота и попадают в очередь догоняния, а не отправляются немедленно. Покрыто регрессионным тестом.
- Статус контейнера Instagram `PUBLISHED` подтверждает публикацию; сохранённый ID публикации восстанавливается, новая публикация не отправляется. Время хранения исходника отсчитывается с момента подтверждения. Живой API пока не проверен.
- Чтение результатов публикаций при получении состояния и очистке файлов выполняется один раз с группировкой по ролику. Назначения, которые не изменились, повторно не записываются.
- Удалены неиспользуемые импорты и неиспользуемое поле планировщика. Восстановление YouTube-сессии добавлено последующими изменениями, описанными ниже.
- На момент этой стабилизации оставались классификация ошибок, календарь догоняния и восстановление загрузок. Их последующее состояние описано ниже; TikTok и проверка реальных аккаунтов по-прежнему требуют внешнего доступа.

## Инвентаризация дальнейшей работы (2026-11-02)

Приоритет основан на последствиях для публикаций, исходников и соседнего сервиса. Это перечень обнаруженных задач, доступных для работы в репозитории без аккаунтов и доступа к серверу; он не гарантирует отсутствия других дефектов.

### Критический приоритет

1. **Восстановление после сбоя до отправки и неоднозначного ответа.** Автоматически повторять только заведомо безопасные операции; после таймаута публикации выяснять результат по ID/сессии, не создавая дубликат. Разграничить сетевые сбои, отказ в доступе и ошибки с неопределённым результатом; ограничить частоту повторов и сохранить исходный часовой срок.
2. **YouTube resumable upload.** Проверять состояние сохранённой сессии, продолжать с подтверждённого смещения и сохранять ID; учитывать истечение сессии, рестарт, частичную отправку и неизвестный результат завершающего запроса. Протокол проверить контрактными тестами; реальная совместимость требует живого API.
3. **Instagram восстановление контейнера.** Проверить обработку всех подтверждённых и отказных состояний, сбои чтения статуса и рестарт на каждом шаге, не отправляя повторный media_publish при неясном результате.
4. **Конкурентность и долговечность очереди.** Проверить прерывание между записью состояния и внешним запросом, транзакционность перестроения и ручных действий, пересечение запросов с работающим worker и поведение при сбое БД/нехватке диска.
5. **Защита файлов.** Проверить параллельные загрузки, учёт временных файлов и резерва диска, аварийную очистку временных файлов, активную передачу при удалении и точные 24 часа после всех трёх подтверждений.

### Высокий приоритет

6. **Планирование и догоняние.** Проверить занятые слоты, несколько долгов, границы часа, переходы суток МСК, ручные закрепления и восстановление после длительного простоя. Открытые продуктовые вопросы не выдавать за согласованные правила.
7. **Отображение догоняния.** Показывать в календаре фактические отдельные назначения восстановления по площадкам и явно отличать их от общего плана; корректно отображать неопределённые результаты и требуемое действие.
8. **Работа с подключениями.** Точно отображать ошибки и необходимость повторного входа, проверять сроки и ротацию токенов, не затирать рабочие данные неполными ответами, не раскрывать секреты в журнале и интерфейсе.
9. **Обработка медиа и запросов.** Контрактно проверить неверные, неполные и повреждённые файлы; безопасность временных ссылок, лимиты и остановку клиентской загрузки; избегать чтения целых видео в память.
10. **Тесты надёжности.** Добавить тесты перезапуска, отказов на каждом шаге, конкуренции, свойств планировщика и сквозных локальных сценариев без вызовов реальных платформ; сохранять общий порог 90%.

### Поддерживаемость и готовность к эксплуатации

11. Упростить крупный HTTP-модуль по контрактам, устранить подтверждённые дублирования и неиспользуемый код, не вводить лишних абстракций.
12. Улучшить диагностируемость: состояния очереди, понятные сообщения и безопасные структурированные журналы без токенов; определить процедуру проверки и восстановления базы.
13. Проверить конфигурацию ресурсов, права каталогов, изоляцию, запуск и откат на локальных фикстурах; фактический сервер и deployment сейчас не трогать.
14. Уточнить документацию: текущий статус функций, ограничения, результаты тестов, ручные шаги подключения и неподтверждённые решения.

### Внешние зависимости и отложенные решения

Реальные OAuth и публикации YouTube/Instagram, допустимый публичный TikTok Direct Post, данные приложений и ограничения сервера нельзя подтвердить только кодом. Заморозка площадки, отказ от публикации и политика резервирования видео требуют продуктового решения; их не вводить молча. Автохэштеги можно спроектировать отдельно без обещания качества и без отправки названий внешнему сервису без решения владельца.

### Выполнено в текущей итерации

Ошибка получения или обновления токена до начала отправки теперь помечается как безопасная для повтора. В пределах часа выполняется повтор не чаще раза в минуту, после границы — по расписанию догоняния; неизвестный результат самой отправки по-прежнему не повторяется автоматически. Постоянный отказ доступа также остаётся в ограниченной очереди повторов; отдельная диагностика отозванных прав ещё нужна.

### Восстановление YouTube — очередная итерация

Сохранённая resumable-сессия теперь проверяется запросом состояния: при частичной загрузке отправляются только неподтверждённые байты, при завершённой сохраняется возвращённый ID. После рестарта задание с проверенной локальной сессией возвращается в обработку. Истёкшая сессия, некорректное смещение или неоднозначный ответ не запускают новую загрузку. Покрыто локальными контрактными тестами, живой API ещё не проверен. При сбое без перезапуска задание с неизвестным результатом по-прежнему требует ручного повтора; автоматическую сверку, политику истёкшей сессии и дополнительные сбои ещё предстоит доработать.

### Автоматическая сверка без перезапуска

Временный сетевой сбой, 429, 5xx или частичное подтверждение сохранённой YouTube-сессии ставит ограниченный повтор по согласованному расписанию; перед отправкой байтов сессия проверяется заново. Ошибки чтения статуса известного YouTube ID и существующего Instagram-контейнера тоже повторяются безопасно. Ошибка запроса публикации Instagram, истёкшая сессия YouTube и другие неопределённые состояния не вызывают слепую публикацию и требуют дальнейшей обработки. Это контрактные тесты без реального API.

### Учёт места после прерывания

Дисковый бюджет учитывает зарегистрированные ролики и фактические незарегистрированные файлы, включая частичные загрузки; если файл больше записанного размера, учитывается больший размер. Это не удаляет возможные исходники и не подменяет проверку свободного места. Диагностика и безопасное восстановление осиротевших файлов остаются отдельной работой.

### Неоднозначная публикация Instagram

Перед `media_publish` сохраняется признак отправки. При потере ответа панель повторно проверяет существующий контейнер: `PUBLISHED` подтверждает успех; если контейнер всё ещё `FINISHED`, повторная команда автоматически не отправляется и требуется проверка. Сброс признака при ручном повторе допускается только после явного подтверждения отсутствия поста и выполняется в транзакции с изменением задания. Это проверено контрактными тестами; реальные ответы и задержки Meta не проверены.

### Конкуренция worker и действий пользователя

Редактирование и перестановка сначала фиксируют все наступившие слоты: ролик нельзя незаметно изменить в промежутке между временем публикации и следующим тиком worker. Если одна задача площадки неожиданно завершилась с ошибкой за пределами обработки API, worker ждёт завершения остальных параллельных задач перед снятием блокировки следующего тика. Оба случая подтверждены регрессионными тестами; это не проверка нескольких независимых процессов панели.

### Защита от нескольких экземпляров и календарь восстановления

Перед запуском HTTP и worker процесс захватывает отдельную эксклюзивную SQLite-блокировку каталога данных. Второй процесс с тем же каталогом не начинает работу; блокировка освобождается операционной системой при завершении процесса. Проверено отдельными процессами; это не распределённая блокировка для сетевой файловой системы. Worker запускается только после успешного открытия порта.

Календарь показывает отдельные догоняющие события для pending/failed/blocked после льготного часа с названием площадки; неизвестный результат и обычные проверки обработки не выдаются за назначенную публикацию. Проверены недельное и месячное представления в браузерном сценарии.

### Корректная остановка worker

При SIGTERM сервер прекращает приём запросов и новые тики, затем ожидает завершения текущих операций площадок до освобождения блокировки и выхода. Принудительное завершение системы может оборвать ожидание; тогда остаётся действующая логика восстановления после аварии.

### Неполные ответы Instagram

Ответ создания контейнера проверяется до сохранения ID и запроса состояния. Неизвестный или отсутствующий статус контейнера не считается бесконечной обработкой: назначается ограниченный повтор проверки. Результат самого запроса создания с неясным ID остаётся неопределённым, без слепой повторной отправки.

### Сохранность после успешной записи и видимость файлов после обрыва

Если после перемещения проверенного видео произошла ошибка, конечный MP4 не удаляется: база уже могла подтвердить транзакцию. Незарегистрированные и незавершённые файлы отображаются количеством в панели и продолжают учитываться бюджетом; активная загрузка не считается брошенной. Имена файлов через состояние панели не раскрываются. Автоматическое восстановление названия и повторное включение файла в очередь не реализованы, поскольку эти данные могли не сохраниться.

Панель также показывает количество записанных исходников, отсутствующих на диске, не раскрывая имена файлов. Проверка не восстанавливает содержимое и не является резервной копией; если файл возвращён на место, предупреждение исчезает при обновлении состояния.

### Отсутствующий исходник и публикация

Перед созданием новой загрузки YouTube или контейнера Instagram проверяются наличие обычного файла и его ожидаемый размер. Недоступный или обрезанный файл получает отдельную понятную ошибку и безопасный повтор по расписанию. Уже существующий контейнер или сессия могут подтвердить завершённую публикацию даже при отсутствии локального файла. Проверка размера не является проверкой целостности по хешу.

### Ручная копия базы

Добавлена команда создания согласованного SQLite-снимка вместе с ключом в новом закрытом каталоге и признаком завершения. На временной базе проверено восстановление очереди и зашифрованных настроек; существующая копия не перезаписывается. Видео в копию не входят, автоматическое расписание копирования и хранение вне исходного диска не настроены.

## Последовательная работа в коде (2026-11-03)

Область задачи: только dev и локальные фикстуры. Main и VPS не изменяются, реальные аккаунты не используются.

1. Отказ авторизации отличается от временной ошибки. Статус повторного подключения сохраняется при рестарте; токены/ID остаются. Неудачное переподключение не скрывает предупреждение, успешное снимает его. Ротация refresh token сохраняется. Проверено red → green тестами адаптеров и worker.
2. Истёкшая YouTube-сессия (404/410) не запускает новую загрузку автоматически. Подтверждённый пользователем ручной повтор сбрасывает только истёкшую сессию без известного ID. Действующие сессии сохраняются. Проверено red → green тестами адаптера и настоящего HTTP/SQLite.
3. Retry-After при HTTP 429 сохраняет паузу всей площадки, включая следующие ролики и рестарты. Секунды/HTTP-date и неверные значения проверены; граница часа не продлевается. Контрактные тесты проверяют ограничения при создании/отправке/сверке YouTube и создании/проверке/публикации Instagram. Сохранённые ID и маркер неоднозначной публикации не сбрасываются.

### Что остаётся

- Живые OAuth/публикации YouTube и Instagram, допустимый публичный TikTok, серверный preflight и пилот — внешние этапы; кодовые тесты их не заменяют.
- Незарегистрированные завершённые исходники восстанавливаются офлайн через `npm run recover` с явно заданными метаданными. Отсутствующие/повреждённые исходники по-прежнему требуют исходного файла или резервной копии. Автоматическое удаление таких файлов запрещено.
- Заморозка площадки, отказ от публикации и резервирование самих видео требуют продуктового решения. Автохэштеги остаются отложенным расширением.
- Регулярное резервирование БД/ключа, проверка реального restore/rollback и наблюдение ресурсов должны быть настроены при будущем этапе эксплуатации. Восстановленная старая очередь требует сверки с соцсетями до запуска worker.
- HTTP-маршруты можно дальше разделять по контрактам; это задача поддерживаемости, а не доказательство отсутствия дефектов.

Финальная локальная проверка 2026-11-03: `npm run coverage` завершился успешно — 142 теста приложения, браузерный smoke/UI, TypeScript и production build. Объединённое покрытие всего src: строки 98.62%, statements 98.38%, ветви 93.72%, функции 96.62%. Отдельно прошли 6 Python-тестов release receiver на временных фикстурах. Реальные API и VPS в этой итерации не вызывались.

### Следующая итерация: найденные функциональные сбои

- Исправлен ручной повтор после терминального состояния YouTube/Instagram: раньше повтор использовал тот же окончательно отказавший ID. Теперь сброс касается только подтверждённого пользователем случая и одной площадки.
- Исправлена защита ближайшего видео: ручной обычный контент при достаточном запасе больше не сдвигает ближайший ролик на более ранний слот. Исключение для покрытия остальных дней при нехватке сохраняется.
- Страница подключений показывает предупреждение об отозванном доступе даже при сохранённом имени аккаунта; успешное отключение убирает предыдущую ошибку.
- Escape во время загрузки больше не закрывает нативный dialog в обход блокировки занятой формы. Проверка воспроизводит удерживаемый HTTP-запрос в браузере.
- Добавлено офлайн-восстановление незарегистрированных файлов и общая проверка MP4; тесты используют настоящий ffprobe, SQLite и эксклюзивную блокировку, проверяют отказ БД и запрет перезаписи.
- Проверка структуры ответов OAuth и ID загрузки не позволяет записать объект/число/пустую строку как ID аккаунта или опубликованного видео. Отсутствующий YouTube ID также допускает подтверждённое ручное восстановление вместо бесконечной проверки того же ID.
- Начатые отправки привязаны к ID канала. Незавершённая публикация не может незаметно перейти в другой аккаунт при переподключении; привязка переживает отключение токена и ручной повтор.
- Воспроизведены и исправлены гонки refresh/OAuth с отключением и новым подключением: поздний ответ не возвращает старые токены и не помечает новые как отозванные. Операция прекращает последующие запросы после смены подключения, сохраняя уже полученный ID контейнера.
- Изменение OAuth-приложения и сброс токена выполняются одной транзакцией: ошибка БД не оставляет половину новой конфигурации.

Итог этой итерации: 172 теста приложения и браузерные сценарии прошли, TypeScript и production build успешны. Полный gate всего src: строки 98.70%, statements 98.48%, ветви 94.22%, функции 96.87%. Прошли 6 отдельных тестов механизма релиза. В браузере проверены desktop/mobile, видимое предупреждение о доступе и Escape во время удерживаемого запроса загрузки; ошибок выполнения нет. Реальные аккаунты и сервер не использовались.

### Согласованность ключа резервной копии

Перед записью ключа в снимок проверяется, что ключ на диске совпадает с ключом открытой базы. При несовпадении отметка завершения не создаётся: копия не выдаётся за пригодную к восстановлению с неправильным ключом. Истёкшие сессии и некорректные ID обрабатываются общей логикой, добавленной ранее в dev, без параллельных схем восстановления.


### Поддержание подключений в простое и формат файлов

При пустой очереди worker проверяет подключения YouTube и Instagram не чаще раза в час и инициирует обновление токена, когда это требуется; сетевые ошибки повторяются позднее, ограничения частоты учитываются, явный отзыв доступа сохраняет предупреждение. После перезапуска проверка выполняется снова; токены хранятся в прежнем защищённом хранилище. Работоспособность реальных API пока не проверена.

Общая для загрузки и восстановления проверка файла учитывает опубликованные Meta ограничения кодеков, частоты кадров, размера изображения и аудио; сообщения об ошибке показываются без вывода секретов. Набор проверок не доказывает приём видео Instagram.
